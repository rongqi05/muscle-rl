## 1. 阶段一：复现并定位基线

### 1.1 加载语义核实（任务书第一阶段第 2 条）

| 项 | 官方 A | v1 / v2 / v3 / v4 |
|---|---|---|
| actor/critic | `checkpoint/best_model.zip` | 官方权重上微调后的 `last_model.zip` |
| 归一化 | `checkpoint/best_env.zip` | 同左，且 `training=False`、`norm_reward=False`、`clip_obs=10.0` |
| 加载 | `SAC_DynSyn.load` + `patched_float_schedule()` | 同左，另显式重建 `ReplayBuffer`/优化器 |
| 动作维 | `nu=700`（138 肌群组），`MuscleNormWrapper` 做 `[-1,1]→[0,1]` | 完全相同（**接口未改**） |

| `dynsyn_weight_amp` | checkpoint 存 `None`（`k=5e-9`,`a=3e7`,`num_timesteps=4.5e7`）→ 上游 `train()` 会算出 **0.075** 并静默改动作语义 | **显式固定 0.0**（`weight≡1`） |

**`terminated` / `truncated` 的严格区分**（已在代码与测试中固化）：

| 情形 | terminated | truncated | `termination_source` |
|---|---|---|---|
| 骨盆高度/倾角/速度越界、侧向任务失败 | **True** | False | `physical_fall` / `task_lateral_drift` |
| 数值异常 | **True** | False | `numeric_anomaly` |
| 达到规定时长 | **False** | **True** | `time_limit` |
| 达到本地步数上限 | **False** | **True** | `step_cap` |

### 1.2 **发现并修复的真实缺陷：`time_limit` 被 `step_cap` 抢先**

`data.time` 由 `timestep=0.002` 逐步累加，走满 N 步后的典型值是 `N·dt − 4e-16`。
原实现用 `sim_time >= time_limit_s` 直接比较，于是**在时长恰为 dt 整数倍时**
（4 / 6 / 10 / 20 s 全是这种情况）时间判据失败，紧接着的步数上限判据抢先触发：

```
[课程] 阶段 s4 (4s) 验证: 成功率=0.00 走满率=0.00 平均存活=4.00s 结束原因={'step_cap': 5}
```

后果**不是显示问题**：评估里「走满规定时长」只认
`termination_source == 'time_limit'`，所以**即使策略完美走满 20 s，也会被记为未完成，
18/20 的门槛永远不可能达成**。既有 v1/v2 的结论之所以没被污染，是因为它们的回合在
约 5 s 就因跌倒结束，从未触及 20 s 边界。

**修复**：时间判据改用**实际经过时间**并给 1 ns 容差（远大于累加误差 ~4e-16，
远小于一个物理步长 2 ms）；步数上限保持 `>=`，使显式的 `max_control_steps` 语义不变。
新增回归测试 **T18** 覆盖 0.4 / 1.0 / 4.0 / **20.0** s 四个整数倍时长。

### 1.4 失稳前 1–2 s 的时间对齐诊断

`scripts/diagnose_prefix.py`，种子 301–305，按「距终止还有多少秒」对齐 5 个回合。

**领先量（中位，相对终止时刻）**：

| 策略 | 领先顺序 |
|---|---|
| **A 官方** | 倾角 **+0.86 s** → 动作饱和 +0.56 → 侧向速度 +0.36 → 侧向偏移 +0.12 |
| **B v1** | **侧向偏移 +1.26 s → 侧向速度 +1.12 s** → 倾角 +0.72 → 动作饱和 +0.34 |

**终止前 2 s 的量级（5 回合均值）**：

| 量 | A 官方 | B v1 |
|---|---|---|
| 骨盆高度 t−2.0 s / t−0.4 s / 末值 | 0.901 / 0.875 / 0.684 | 0.905 / 0.861 / **0.532** |
| 高度 >0.85 m 的步占比 | 86% | 80% |
| 最后 0.4 s 的高度下降占总下降 | **88%**（0.191 / 0.217 m） | **88%**（0.330 / 0.373 m） |
| 末段下沉速率 | 0.48 m/s | **0.82 m/s** |
| 倾角 均值 → 末段 | 13.8° → **61.6°** | 5.8° → **15.8°** |
| 侧向偏移 均值 → 末段 | 0.079 → 0.374 m | **0.138 → 0.437 m** |
| 侧向速度 均值 → 末段 | 0.283 → 1.330 m/s | 0.299 → 0.933 m/s |

| 触地足数 均值（0 足触地占比） | 2.24（1%） | 2.02（1%） |

**读法（严格区分观察顺序与因果）**：

* **观察到的顺序**：v1 在终止前 2 s 里，侧向偏移/侧向速度**先**偏离；倾角一直很小
  （末段仅 15.8°），骨盆高度在前 1.6 s 基本不变、最后 0.4 s 突然崩掉。
  即 v1 的失败模式是**「边漂边下沉」**，与官方策略的**「先倾后倒」**不同。
* **因果**：以上只是时间顺序，**不构成因果**。要判定"侧向漂移导致高度崩掉"需要单因素
  反事实实验，本轮未做（见 §7 的未验证假设）。
* 早期观察到的"侧向漂移是主因"在本阶段被**修正**为"v1 的终末事件是高度塌陷，
  侧向漂移是其前兆之一"。

## 2. 阶段二：修复训练流程（课程阶段切换）

### 2.1 修复前的事实

`scripts/train_healthy.py` 的 `main()` 里写死了 `stage = stages[0]`，`BudgetCallback`
**不做任何阶段切换**。所以「配置里列出 6/10/20 s」只是配置，**课程从未实现**：
v1/v2/v3 之前的每次训练都只在单一阶段时长下进行。这正是任务书第二阶段第 1 条指出的问题。

### 2.2 实现内容

新增 `CurriculumCallback`（`scripts/train_healthy.py`）与
`ResearchLocomotionEnv.configure_episode_seconds`（`hemirl/research_env.py`）：

| 要求 | 实现 |
|---|---|
| 由验证结果触发升级 | 每 `val_every_transitions` 在**独立验证种子（101–105）**上评估；成功率 ≥ `promote_val_success_rate`(0.8) **且**本阶段已攒够 `min_transitions` 才升级 |
| 阶段验证用同一套规则 | `quick_eval` 用 `env_spec` 构建，**与训练同终止判据、同时长**；成功还要求速度/侧偏/倾角/数值判据 |
| 训练环境更新 | `vec_env.env_method("configure_episode_seconds", s)` 广播到**全部 worker**；不重建 `SubprocVecEnv`（重建会丢 worker 状态、重新加载模型，并使 `VecNormalize` 挂载关系需要重建） |
| 阶段记录 | 每次 start/validate/promote/stalled/end 都落盘 `curriculum_history.json`，并写入 `train_meta.json` |
| 断点恢复 | `--resume` 走同一装配路径，恢复后重新施加显式的 lr/amp 固定；历史 append-only |
| 不达标不晋级 | 停滞只记录 `stalled` 事件，**不降低门槛** |

### 2.3 为什么起步阶段是 4 s（这不是"降低验收标准"）

v1 的课程从 6 s 起步，而官方策略只能走约 4.7 s、v1 约 5.6 s → 6 s 阶段成功率恒为
**0.00**，课程**永远不会升级**（上一阶段报告 §6.2 已记录该现象）。
把起步设为 4 s 是「设计可验证的较短阶段」，**最终 s20 阶段与 `eval.success` 的
质量阈值一字未改**，20 s 验收门槛也一字未改。

### 2.4 新增测试

| 测试 | 覆盖 |
|---|---|
| **T16** | 运行时改回合时长：派生量同步重算、真的改变截断时刻、`None` 回到官方口径、非法值报错且不污染状态 |
| **T17** | 单因素保证：改时长**不**改变终止判据与奖励分量 |
| **T18** | 时长恰为 dt 整数倍（0.4/1.0/4.0/**20.0** s）必须以 `time_limit` 结束 |
| **C1–C9** | 课程：不达标不升级 / 达标升级并广播到全部 worker / `min_transitions` 是"最早可评估"门槛 / 停滞只记录不晋级 / 预算仍生效 / 最高阶段不再升级 / 历史落盘 / `env_spec` 传递完整且可 pickle / 真实配置的阶段单调且验证与测试种子不相交 |

结果：`tests/test_research_env.py` **18/18**、`tests/test_curriculum.py` **9/9**。

## 3. 阶段三：受控实验

### 3.1 两个可检验假设（附诊断指标）

**H1（奖励配比）**：奖励由「骨盆高度存活」主导。存活项只检查 `高度 ≥ 0.55 m`，
而实测在该窗口内高度 >0.85 m 的步占 80%，**即存活项在关键窗口内恒为常数、对"即将下沉"
零区分度**；同时它把参考跟踪项的相对权重压低，且 v1 的动作饱和（0.114）明显低于官方
（0.200），末段下沉速率却高 1.7 倍。
→ *诊断指标*：动作饱和、末段下沉速率、各奖励分量的量级。

**H2（数值/更新量）**：价值函数在 2083 次更新下未收敛，导致长时信用分配错误。
→ *诊断指标*：多回合的 Q 与经验回报的校准（**不以单点 Q/MC 比值断言**）。

### 3.2 E1：课程阶段切换（v3 = v1 + 已实现的课程）

终止判据、`train_freq`、并行数、buffer、预算**逐位相同**；侧向终止**显式关闭**（`null`，
不沿用 v2 的 0.10 m 方案）。

**10 s 档**：全部 **0/20**；存活与 20 s 档完全相同（A 4.96 / B 5.56 / C 5.29 / D 5.02 / E 3.83）。

**6 s 档**（唯一有策略能走满的档位）：

| 策略 | 走满 | 存活 (s) | 速度 (m/s) | 侧偏 (m) | 倾角 | 终止来源 |
|---|---|---|---|---|---|---|
| A 官方 | 0/20 | 4.96 | 0.892 | 0.429 | 58.7° | `physical_fall`×20 |
| B v1 | **5/20** | **5.49** | 0.953 | 0.375 | 21.8° | fall×15, `time_limit`×5 |
| **C v2** | **6/20** | 5.20 | 0.881 | 0.382 | 26.5° | `time_limit`×6, fall×14 |
| D v3 | 1/20 | 4.99 | 0.914 | 0.592 | 30.4° | fall×19, `time_limit`×1 |
| E v4 | 0/20 | 3.83 | 0.892 | 0.328 | 44.2° | `physical_fall`×20 |

读法：

* **没有任何策略在任何档位达标**（6 s 档最好 6/20，远低于 18/20；10 s 与 20 s 档全为 0/20）。
* **E2（`w_survival` 100→20）在每一档、每一项上都更差**：6 s 走满 0/20、存活 3.83 s（最差）、
  倾角 44.2°（最差）、动作饱和 0.184（最高，即动作更激进）。
  → **H1 被否定，而且证据指向的是相反方向**：降低存活项使策略更激进、更早跌倒。
* **E1（课程）在同预算下没有改善目标指标**：6 s 走满 1/20（v1 为 5/20），20 s 存活 5.02 s
  （v1 为 5.56 s），且侧偏最大（0.596 m）。合理的解释是：课程把这 5×10⁴ 预算的一部分
  花在了 4 s / 5 s 两个更短的阶段上（约 2.1×10⁴ transitions 才通过 s5），
  而 v1 把全部预算直接花在 6 s 上。**课程机制本身按设计工作，但按当前配置它对 20 s 目标是
  预算不划算的。**
* **异常与退化行为全为 0**：没有数值异常，没有"站着不走"。所有结束都是真实动力学跌倒。

## 5. 价值函数校准（用多回合，而非单点）

`scripts/compare_policies.py --seeds 301:305`，在 5 个种子上各取轨迹初始状态，
比较 critic 的 $Q(s_0,a_0)$ 与该轨迹的经验折扣回报 $G_0$：

| 策略 | $Q/G$ 均值 ± 标准差 | 逐种子 |
|---|---|---|
| A 官方 | **0.832 ± 0.061** | 0.788 / 0.894 / 0.821 / 0.907 / 0.750 |
| B v1 | **1.141 ± 0.101** | 1.058 / 1.186 / 1.095 / 1.318 / 1.050 |

**方法论修正（重要）**：上一阶段只用**单点** $Q(t_0)/G(t_0)$ 得到「官方 0.989、微调 1.376」，
据此把「价值函数高估 38%」当作下一步的依据。多回合重测后，真实情况是
**官方 0.832 ± 0.061（低估）、v1 1.141 ± 0.101（高估约 14%）**——单点比值把失准幅度
放大了 2–3 倍，而且官方 critic 的方向是低估而非准确。

→ **H2 的证据被显著削弱**：critic 的失准只有约 ±15%，不足以支撑「增加梯度更新次数
就能解决问题」的断言。本轮**没有**改 `train_freq`，也**不**建议仅凭该比值去改。

## 6. 明确结论

### 6.1 是否达到 18/20？

**未达到。** 独立测试集 301–320 上，20 s 走满：A/B/C/D/E 全部 **0/20**；
6 s 走满最好 **6/20**。按预定义门槛（≥18/20 且满足速度/侧偏/倾角判据、无数值异常、无隐藏支撑）
判定为**不通过**。

### 6.2 本轮的最好真实结果

**B（v1）仍是全五档中最好的策略**：20 s 存活 **5.56 s**、速度 0.955 m/s（目标 1.038）、
最大侧偏 0.406 m、最大倾角 25.0°，6 s 走满 5/20。
本轮的 D（课程）与 E（配比）**都没有超过它**。

### 6.3 失败集中发生的时间与状态

* 时间：所有策略在 **4.8–5.6 s** 之间终止，10 s 与 20 s 档的存活时间与 6 s 档几乎相同
  → **存在一道约 5 s 的墙**，与要求的 20 s 相差 4 倍。
* 状态（终止前 2 s，5 回合，见 §1.4）：骨盆高度在最后 0.4 s 贡献了 **88%** 的总下降，
  下沉速率 0.82 m/s（官方 0.48 m/s）；而 v1 的倾角始终很小（末段仅 15.8°）。
  → 这是一种**快速的高度塌陷（下沉）**，不是缓慢倾倒。
* 侧向偏移/侧向速度在 v1 上**先于**高度塌陷约 1.1–1.3 s 出现（观察顺序，非因果）。

### 6.4 本轮已排除的原因

1. 观测裁剪（上一阶段命名对照：4.62 → 4.61 s，5/5 仍倒）；
2. 归一化统计被污染（四个策略与官方**逐位相同**）；
3. 奖励定义不一致（v3/v4 的 `extra_reward` 与 v1 逐位相同）；
4. 加载路径/复现口径（与既有报告**逐位一致**）；
5. **课程机制未实现**（已修复并验证）；
6. **`time_limit` 被 `step_cap` 抢先**（已修复；修复前 18/20 门槛**不可能达成**）；
7. **`w_survival` 过高**（E2 直接检验：降低它使每一档都变差）；
8. **critic 严重失准**（多回合实测仅 ±15%，且官方是低估）。

### 6.5 尚未验证的假设

1. **侧向漂移是否"导致"高度塌陷**——只有时间顺序，没有反事实实验。
2. **提高存活项权重是否有益**——E2 只测了降低；单调趋势提示相反方向，但未验证。
3. **"5 s 墙"是否由 6 s 回合的截断-自举结构造成**——策略从未真正到达 6 s，
   因此"活到 6 s"几乎得不到正向信号；这一假设未设计实验。
4. **增加更新次数是否有效**——因校准证据不足，本轮有意未测。

### 6.6 下一次**单项**实验

**E3：在 v1 配置上把 `reward_split.w_survival` 从 100 提到 300，其余逐位不变。**

**依据**：E2 是本轮唯一的单因素奖励实验，它给出的方向是**单调的**——把存活项从 100 降到 20
使每一档、每一项指标都变差（6 s 走满 0/20、存活 3.83 s、倾角 44.2°、动作饱和 0.184）。
既然下调有害，上调是同一轴上最直接的下一格。

**必须同时报告**（按任务书要求）：行走表现（三档时长）、逐奖励分量、动作饱和、
以及**多回合**价值校准。**不得**只看训练回报。

```bash
# 1) 从 v1 配置派生 v5，只改一个键：reward_split.w_survival: 100.0 -> 300.0
#    （保留 v1 的 6 s 起始阶段、无侧向终止、train_freq=2）
# 2) 试训练（5×10⁴ transitions / 30 min 上限）
MUJOCO_GL=egl PYTHONPATH=. python scripts/train_healthy.py \
    --config configs/train_healthy_v5.json --max-transitions 50000 --max-minutes 30
# 3) 三档时长评估（测试集 301-320 不变）
MUJOCO_GL=egl PYTHONPATH=. python scripts/eval_healthy.py \
    --config configs/train_healthy_v5.json --policies B=runs/train/healthy_v1 F=runs/train/healthy_v5 \
    --seeds 301:320 --episode-seconds 20 --tag phase6_eval_20s
# 4) 多回合价值校准
MUJOCO_GL=egl PYTHONPATH=. python scripts/compare_policies.py \
    --config configs/train_healthy_v5.json \
    --policies A=artifacts/checkpoints/LocomotionFull B=runs/train/healthy_v1 F=runs/train/healthy_v5 \
    --seeds 301:305 --out reports/train_vs_baseline_phase6.json
```

**若 E3 也无效**，则本轮所有单因素证据都指向同一结论：**瓶颈是训练预算**，
而不是奖励配比、终止设计或更新频率。

**资源估算（供安排更长训练）**：本机实测 **44 transitions/s**（12 并行、train_freq=2，
含课程验证开销；纯训练约 70/s）。v1 用 5×10⁴ 把 20 s 存活从 4.96 s 提到 5.56 s、
把 6 s 走满从 0/20 提到 5/20。若要在同样斜率的延长线上从 5.5 s 推到 20 s，
按至少 4–10 倍的预算估计：

| 预算 | 预计墙钟 | 说明 |
|---|---|---|
| 2×10⁵ | ≈ 75 分钟 | 第一次有意义的放大 |
| 5×10⁵ | ≈ 3.2 小时 | 强烈建议的运行量级 |
| 2×10⁶ | ≈ 12.6 小时 | 上游官方 checkpoint 用了 5×10⁷ transitions（本机不可行，仅作参照） |

**这些都不应自动开启**，需要显式确认。
